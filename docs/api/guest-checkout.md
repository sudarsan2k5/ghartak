# Guest checkout API

Village customers place Cash on Delivery orders without creating an account. There is no OTP, password, email, PIN code, GPS, or delivery-zone check in this milestone. The public catalogue is unchanged. Successful checkout also returns a tracking capability token. See [order status](order-status.md).

All paths are under `/api/v1`. Money is integer paise. Shared Zod contracts live in `@ghartak/contracts`.

## `POST /checkout/guest`

Request body (strict; extra financial or inventory fields are rejected):

```json
{
  "customerName": "Ramu",
  "customerPhone": "9876543210",
  "deliveryAddress": "House near the school, Demo Village",
  "items": [{ "productId": "10000000-0000-4000-8000-000000000031", "quantity": 2 }],
  "idempotencyKey": "mobile-generated-unique-key"
}
```

| Field | Rules |
| --- | --- |
| `customerName` | Required, trimmed, 1–120 characters |
| `customerPhone` | Indian mobile, 10 digits starting 6–9. `+91`, `91`, or a leading `0` are accepted and stored as `+91XXXXXXXXXX` |
| `deliveryAddress` | Required free-text, trimmed, 1–500 characters. No PIN, locality, landmark, or GPS fields |
| `items` | 1–40 lines. Valid product UUIDs. Quantity 1–999. Duplicate product ids are merged by summing quantity |
| `idempotencyKey` | 8–128 characters, generated by the client |

The client must not send prices, totals, delivery fees, stock, or status. The server reads current central listings.

Success `200`:

```json
{
  "orderNumber": "GT-A1B2C3D4E5F6A7B8",
  "status": "placed",
  "paymentMethod": "cash_on_delivery",
  "paymentStatus": "pending",
  "customerName": "Ramu",
  "items": [
    {
      "productId": "10000000-0000-4000-8000-000000000031",
      "productName": "Toor Dal",
      "quantity": 2,
      "unitPricePaise": 12000,
      "lineTotalPaise": 24000
    }
  ],
  "subtotalPaise": 24000,
  "deliveryFeePaise": 0,
  "totalPaise": 24000,
  "createdAt": "2026-10-30T18:30:00.000Z",
  "trackingToken": "base64url-hmac-token"
}
```

The response does not include the phone number, address, internal order UUID, or stock. `orderNumber` is a non-guessable `GT-` + 16 hex characters. There is no public GET for an order. `trackingToken` is a capability for `GET /orders/status`. It is not stored in `guest_checkout_requests.response`. The database keeps only a SHA-256 hash, expiry, and optional revocation timestamp.

### Error codes

| Status | `error.code` | When |
| --- | --- | --- |
| 400 | `request_error` | Validation (name, phone, address, items, extra fields) |
| 409 | `product_unavailable` | Missing, unpublished, inactive, inactive category, or not listed as available. `productId` is included |
| 409 | `insufficient_stock` | Requested quantity exceeds current stock. Quantity is not reduced. `productId` is included |
| 409 | `idempotency_conflict` | Same idempotency key with a different canonical request |
| 429 | `rate_limited` | More than 20 guest checkout attempts from one IP in 10 minutes |
| 503 | `request_error` | Redis unavailable for the rate limit |

The entire order is rejected if any line fails. No partial order is stored and no other product's stock is changed.

Body size is limited to 32 KiB.

## Idempotency

The mobile client generates `idempotencyKey` before submit and retries the same key after a timeout.

- Keys are stored in `guest_checkout_requests` with a SHA-256 hash of the canonical request (normalized name, phone, address, merged items).
- A unique primary key plus `SELECT FOR UPDATE` serializes concurrent retries.
- A successful retry returns the original order and the same tracking token. The token is recomputed from `ORDER_TRACKING_SECRET` and the order id so a lost response can be recovered without storing plaintext.
- A different body with the same key returns `409`.
- A failed request rolls back, including the idempotency row, so the client may retry.
- Keys are retained with the order (`ON DELETE RESTRICT`). There is no automatic expiry in this milestone; treat keys as long-lived.

## Pricing and delivery fee

`item total = current listing price in paise × quantity`  
`subtotal = sum of item totals`  
`total = subtotal + delivery fee`

The delivery fee is the current `app_settings.delivery_fee` value, snapshotted onto the order as `delivery_fee_paise`. Later fee changes do not rewrite history. The initial value is `0`. Administrators change it with the admin API; customers cannot.

There is no village-specific fee and no client-supplied fee.

## Inventory

One PostgreSQL transaction:

1. Lock the idempotency row.
2. Lock central `store_products` rows in product-id order.
3. Re-read product, category, availability, price, and stock.
4. Read and snapshot the delivery fee.
5. Insert the order, item snapshots, address snapshot, unpaid COD payment, and `placed` status event.
6. Deduct stock, set availability to `out_of_stock` when it reaches zero, and write `removal` movements.

Movements use `actor_user_id = null` (system / guest checkout). The reason is `guest_order:{orderNumber}`. Stock cannot go negative.

## COD lifecycle

Existing order statuses are reused. No new enum values were added.

| Intended business name | Stored status |
| --- | --- |
| Pending | `placed` (created here) |
| Confirmed | `confirmed` |
| Preparing | `packed` |
| Out for delivery | `out_for_delivery` |
| Delivered | `delivered` |
| Cancelled | `cancelled` |

Payment method is `cash_on_delivery`. `orders.payment_status` and `payments.status` stay `pending` until cash is collected. This milestone does not mark COD paid and does not add a payment gateway.

Administrators cancel orders and restore stock with `POST /api/v1/admin/orders/:orderId/cancel`. See [admin orders](admin-orders.md). The same cancellation path covers guest and registered orders. A future customer-facing cancellation API is out of scope.

## Coverage

The first launch does not validate delivery zones, PIN codes, or GPS. Any free-text address is accepted. Coverage checks are a later milestone.
